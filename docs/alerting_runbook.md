# MetricGround 最小失败告警与处置手册

## 目标与边界

本阶段只建立演示环境的最小主动发现能力，不把它描述为生产级监控或 7×24 值班：

- 每小时核对 Sites 项目仍处于可用状态；
- 检索最近 70 分钟的生产 Worker 错误，以覆盖调度抖动；
- 仅在发现新故障、状态恶化、连续失败或故障恢复时通知；
- 状态未变化且无错误时保持安静，避免把定时查询误称为告警；
- 监控不读取或保存用户上传的原始数据行。

受保护站点的 `/api/health` 需要登录身份。当前监控不保存登录 Cookie 或绕过令牌，因此它能主动检查 Sites 控制面状态和 Worker 错误，但不能在无人登录时对 Web/D1 健康接口做匿名合成探测。登录后的 `/api/health` 仍是人工或发布验收的一部分。这个边界必须在简历和面试中明确说明。

当前托管平台的任务频率上限为每小时一次，因此没有把 30 分钟方案伪装成已落地能力。已启用任务为 `MetricGround 最小失败告警`，时区为 `Asia/Shanghai`。

## 告警判定

| 等级 | 触发条件 | 动作 |
|---|---|---|
| P1 | Site 不再是 `active`、当前线上地址缺失，或连续两次监控自身执行失败 | 立即通知，暂停演示并检查部署状态 |
| P2 | 最近窗口出现新的 Worker 异常、5xx 或结构化 `health_check` 的 `degraded` 事件 | 通知并附时间、路由、状态码、requestId/traceId |
| 恢复 | 前一轮处于故障，本轮 Site 恢复且未出现新的错误 | 发送一次恢复通知 |
| 正常 | Site 活跃且没有新的错误 | 不通知 |

## 处置顺序

1. 记录告警时间、Site 版本、路由、状态码、requestId/traceId；
2. 查询同一时间窗口内的 Worker 日志，判断是部署、D1、身份、限流还是应用异常；
3. 对登录用户执行 `/api/health`，确认 Web、D1 与可选模型的实际状态；
4. 复现后先修复根因，再增加自动回归；不通过隐藏失败或放宽校验恢复“绿色”；
5. 修复发布后复跑核心链路，并保留 CI、线上日志和版本证据；
6. 将故障、原因、修复、回归与残余风险追加到版本说明或评测记录。

## 面试中可以与不可以声称的内容

可以声称：项目具有定时的托管状态检查、Worker 错误检索、失败/恢复通知规则，以及可追溯的故障处置流程。

不可以声称：已经具备公网 SLA、完整 APM、短信/电话升级、跨区域探测、值班轮换或无人登录的 D1 合成监控。
