# MetricGround 面试讲解稿

## 30 秒项目介绍

MetricGround 是面向使用 Excel/CSV 开展经营分析的初级数据分析师的人机协同 Agent。它把一次分析拆成“数据画像—质量检查—口径确认—受控计算—结果验证”，模型负责理解问题和提出计划，程序负责确定性计算；涉及清洗、指标定义和多表关联时必须由用户确认，避免模型直接猜数字或执行高风险操作。

实际部署说明：公开v0.3.9 / Sites版本13保留累计二十次请求的受限Qwen-Plus试验，明确意图仍优先规则。真实网页导出暴露了一个来源误判：v0.3.8的候选计划经过程序补齐和策略处理，不能将所有字段归因于模型。格式1.3新增模型工具决策与程序调整记录；完整CI验证了模拟SDK工具流程、规则/模拟模型下载、持久化与恢复。本轮没有新增云调用，新版真实Qwen工具决策导出尚待验收。

控费迭代案例：发现 SDK 与外层重复重试风险 → 在真实出站位置加入 D1 全站二十次试验计数、每问题两次请求、输出/输入长度与模型白名单 → SQL/fetch 回归及真实工具层小测试 → 完整 CI 和公开关闭状态验收。请求数保护不等于金额硬上限，真实测试、模拟检查和线上规则回归分别报告。

可展示的迭代：口语计数误路由、排名澄清后变成单指标、缺字段自动替代 → 修复识别和共享策略、保留原任务与空字段 → 新增路由/API/浏览器交接回归 → 完整 CI 通过 → 发布 Sites 版本 7 → 10 个线上匿名探针及隔离复测通过。证据见 `evaluation/intent-routing-validation-v0.3.3-2026-10-10.md`。

## 为什么这样设计

初级分析师真正容易出错的地方通常不是不会画图，而是：

1. 不清楚一行数据代表什么，导致重复统计；
2. 直接按同名字段关联，造成孤儿键、N:N 或行数膨胀；
3. 没有说清指标的统计对象、范围、分子和分母；
4. 模型生成的 SQL/Python 看起来合理，但缺少执行前约束和执行后勾稽；
5. 清洗和计算过程无法追溯，面试或复盘时解释不清。

因此项目没有把大模型当计算器，而是让它担任“规划者”；真正改变数据或产生数字的动作由白名单程序完成。

## 模型、程序和人的分工

| 角色 | 负责 | 不负责 |
|---|---|---|
| 大模型 | 理解自然语言、识别任务类型、推荐候选字段、提出澄清问题和工具计划 | 不读取原始明细到云端、不直接生成最终数字、不执行任意代码 |
| 确定性程序 | 字段画像、质量规则、清洗副本、关联画像、聚合、趋势、Top N、结果校验 | 不猜业务口径、不替用户决定关联键语义 |
| 用户 | 确认数据粒度、指标口径、清洗规则、关联关系和风险接受范围 | 不需要手写 SQL/Python 才能完成常见任务 |

## Agent 为什么不是普通表单

每次任务都有 `TaskRun` 状态：规划、待澄清、待批准、可执行、执行中、验证、完成或失败。每个工具调用记录输入摘要、开始/结束时间、结果和失败原因；人工确认也记录在任务轨迹中。非法跳步会被状态机阻止，最终可以导出不包含原始明细行的证据包。

v0.3.9起应分别展示：`modelDecision`说明模型向工具提交了什么分析类型和字段；`planAdjustments`说明程序补齐或约束了什么；候选`AgentPlan`说明系统最终向用户建议什么；`AnalysisSpec`说明人工批准什么；结果与DuckDB SQL说明程序计算并复核什么。工具决策经过参数校验，缺省字段可能被模式补为空字符串，不包含原始HTTP或思考过程。置信度和计划文案由程序设置，不能拿它们证明模型准确率。

## 多表关联怎么工作

两表关联前，程序检查：

- 单键或双字段复合键的空值和唯一性；
- 关系属于 1:1、1:N、N:1 还是 N:N；
- 左右表覆盖率、孤儿键和预计输出行数；
- 是否可能重复累计左表金额；
- 金额候选字段在关联前后的源表合计、关联后合计、重复源行、排除源行和净差额；
- 当前数据版本是否仍和确认时一致。

N:N 默认禁止。三表场景不是一次性盲目合并，而是：

1. 用户确认并锁定步骤 1；
2. Agent 只从已进入结果的数据表中推荐桥接表；
3. 用户重新确认步骤 2；
4. 程序按顺序执行两次关联；
5. 校验每步版本、关系、左连接行数和维表是否放大当前粒度。

金额对账不是简单比较总行数。系统为每条来源记录保留内部血缘：一条订单被商品明细复制两次会被记录为“重复源行”，内连接排除的订单会被记录为“排除源行”。即使二者恰好互相抵消、净差额为 0，也不会误判为安全。风险会随派生数据版本进入指标页，未守恒字段不能继续求和或求平均。

演示样例中，订单表先按 `customer_id` 关联客户表，再由客户表按 `region` 关联区域负责人表。两步均为安全维表关联，4 行订单最终仍为 4 行；未匹配订单保留为空，不伪造属性。

## 哪里会失败

| 失败场景 | 系统行为 |
|---|---|
| 字段不存在或模型输出非法字段 | 停在待确认状态，要求重新选择 |
| 业务问题含糊 | 返回澄清问题，不执行计算 |
| 退款、预测等能力未实现 | 明确拒答，不用 Olist 默认答案替代 |
| 关联键存在 N:N | 阻止执行，建议先聚合或修正键 |
| 关联后金额字段不守恒 | 展示重复与排除证据，并阻止该字段继续求和或求平均 |
| 数据版本在确认后变化 | 原计划失效，必须重新画像和确认 |
| 清洗可能改变业务含义 | 只记录建议，必须二次确认后生成派生副本 |
| 本地模型不可用 | 使用规则降级；不会跳过审批或把模型答案当计算结果 |
| 云端 API 未配置 | 继续使用本地 Ollama，不影响确定性工具 |

## 如何验证结果

验证分为四层：

1. **函数层**：AnalysisSpec、TaskRun、质量规则、关联基数和执行器单元测试；
2. **跨场景层**：订单、营销、库存三类不同字段结构，验证字段识别、计算和拒答；
3. **浏览器层**：真实上传 CSV，完成审批、执行、图表、两表和三表工作流，并检查运行时异常；
4. **独立复算层**：通用工作台固定任务与 pandas 参考结果对账。

通用指标执行还会在浏览器内调用 DuckDB-WASM，以独立 SQL 对同一数据版本复算指标值、参与行数、去重对象和排除边界。主计算与复核仍共享同一上传数据，因此这是实现独立性校验，不是外部审计或源数据真实性证明。

三表端到端回归验证了：桥接表和键推荐正确、两次人工确认生效、两步均保持 4 行、第三表字段进入结果、9 项管线校验通过，并能继续进入画像和后续分析。独立风险用例验证订单金额从 410 变为 470 时，系统识别 1 行重复、1 行排除、净差额 +60，并阻止后续聚合。

## 不应夸大的边界

- 当前是可面试演示和目标用户测试的 MVP，不是生产级企业平台；
- 尚未连接真实公司的数据库、权限和指标治理系统；
- 自动化任务验收不等同于正式用户研究；
- 5 份新人测试文件均通过系统读取，项目所有者手工走通 3 份，但这不等于 3 名新人参与测试；
- 当前比例指标不是任意两个聚合量之比；
- TaskRun 持久化、基础 API 防护、公开 Sites 入口和健康检查已完成。v0.3.2 为降低新人测试登录门槛，临时启用浏览器匿名会话：未登录规划 200、自读 200、交叉读取 404、跨会话覆盖 409；测试后可恢复登录，匿名记录不自动迁移。历史真实设备主流程、移动端冷启动修复与双账号隔离证据保留。每小时最小告警已启用，真实故障通知与正式目标用户研究尚未完成；
- 项目参考 Data Formulator 的交互思路，但 Agent 工作流、质量规则、口径合同、受控执行和测评是独立实现。

## 推荐演示顺序

1. 上传带质量问题的订单 CSV，展示系统不会自动删数据；
2. 展示一个指标口径未确认时无法执行的案例；
3. 完成地区金额分组或 Top N，查看 TaskRun 和结果校验；
4. 上传客户表和区域表，演示三表逐步关联；
5. 上传订单与商品明细表，展示金额不守恒如何传递并阻止后续计算；
6. 展示一个 N:N 被阻止的案例；
7. 导出证据包，说明模型、程序和人工确认分别留下了什么证据。
