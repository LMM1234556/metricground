# MetricGround Agent V1 设计说明

## 1. 产品定位

面向使用 Excel/CSV 开展常见经营分析的初级分析师，设计“数据画像—质量检查—口径确认—受控计算—结果验证”的人机协同 Agent 工作流。

它不是“让大模型直接分析表格并给数字”，而是让模型负责理解与沟通，让确定性程序负责数据处理与计算，让用户在高风险业务语义节点做最终确认。

## 2. 为什么这样设计

初级分析师最容易犯的错误通常不是不会写代码，而是：

- 不清楚一行数据代表订单、订单商品、客户还是库存快照；
- 把字段名当成业务定义，例如把 `amount` 自动理解成收入；
- 在一对多关联后重复累计订单金额；
- 忽略缺失、重复、无效日期、异常值和未匹配键；
- 得到一个数字后没有口径、样本范围和对账证据。

因此系统必须先确认数据和口径，再执行计算；大模型不能绕过这些门禁。

## 3. 总体架构

```text
用户业务问题
  -> 数据版本与字段画像
  -> Agent Planner（意图、候选字段、澄清问题、执行计划）
  -> 人工确认（粒度、质量处置、指标口径、关联关系）
  -> 白名单确定性工具
  -> 结果验证与对账
  -> TaskRun 审计轨迹与证据包
```

`AnalysisSpec` 是模型、页面和计算程序之间的统一合同；`TaskRun` 是 Agent 的状态与审计记录。数据文件发生变化后，版本标识变化，旧计划不能继续执行。

## 4. 模型做什么，程序做什么

| 环节 | 大模型 | 确定性程序 | 人工 |
|---|---|---|---|
| 理解问题 | 识别意图、提出候选字段、生成澄清问题 | 校验字段是否真实存在 | 说明业务目标 |
| 数据画像 | 不读取原始明细行 | 解析 Excel/CSV、推断类型、统计缺失与唯一性 | 确认一行代表什么 |
| 质量检查 | 解释风险及建议 | 执行重复、缺失、有效性、异常和键检查 | 决定保留或后续处理 |
| 指标口径 | 把自然语言转为候选结构 | 校验统计对象、字段、筛选、分子分母 | 确认概念边界 |
| 多表关联 | 解释候选关系 | 计算唯一性、基数、覆盖率、孤儿键和行数膨胀 | 确认键含义和输出粒度 |
| 计算 | 不计算最终数字 | 执行计数、求和、平均、比例、分组、趋势、Top N | 批准执行 |
| 验证 | 解释结果及限制 | 基础校验后由 DuckDB-WASM 独立 SQL 复算，核对指标值、行数、去重对象、排除记录、排序和比例边界 | 复核业务合理性 |

## 5. 状态机

主路径：

```text
IDLE -> DATA_PROFILED -> PLANNING
  -> NEEDS_CLARIFICATION
  -> NEEDS_APPROVAL
  -> READY_TO_EXECUTE
  -> EXECUTING
  -> VALIDATING
  -> COMPLETED
```

异常状态包括 `UNSUPPORTED`、`FAILED`、`NEEDS_REVISION`、`NEEDS_JOIN_REVISION` 和 `DATA_VERSION_CHANGED`。非法跳步会被程序拒绝。

## 6. 多表关联边界

V1 只允许：

- 最多 3 张表或工作表；
- 等值关联；
- 单字段键或最多 2 字段复合键；
- `left join` 和 `inner join`；
- `1:1`、`1:N`、`N:1`；
- `N:N` 默认禁止，必须先聚合或修正关联键。

关联前检查键空值与唯一性；关联时计算匹配覆盖率、孤儿键和预计行数；关联后使用来源行血缘检查实际行数、输出粒度、金额字段重复累计、范围排除和净差额。未守恒字段的求和与平均会被确定性规则阻止。

## 7. 失败方式与处理

| 失败 | 系统行为 |
|---|---|
| 模型不可用或超时 | 回退到确定性规则，不影响已支持工具 |
| 模型返回不存在字段 | 字段校验失败，进入澄清，不执行 |
| 指标口径不完整 | 保持待确认状态 |
| 数据版本变化 | 进入 `DATA_VERSION_CHANGED`，旧计划失效 |
| 多对多关联 | 默认阻止执行 |
| 一对多导致错误粒度 | 要求调整主表、连接类型或先聚合明细表 |
| 计算出现无效值 | 排除并计数，不能静默当作 0 |
| 结果检查失败 | 进入失败或修订状态，不标记完成 |

## 8. 如何验证结果

当前自动验证覆盖：

- 数据版本与执行计划绑定；
- 源数据行数和进入计算行数勾稽；
- 去重统计对象可计算；
- 数值结果有限；
- 比例位于合理边界；
- 分组与 Top N 排序正确；
- 趋势时间顺序正确；
- 关联基数未漂移、输出行数符合预览、未发生多对多；
- 常见金额字段源表合计、关联后合计、重复源行与排除源行可对账；
- 证据包不包含原始数据行且具备完整性校验。

订单、营销、库存三个结构化场景共执行 34 项跨场景测试；Agent 底座、数据目录、关联、状态机和证据包另有独立核心测试。浏览器端还验证了上传、规划、人工确认、Top N 执行和 TaskRun 完成轨迹。

## 9. 模型与 API 策略

默认使用本地 Ollama + Qwen，不需要付费 API。可选 Groq 或阿里云百炼 DashScope OpenAI 兼容接口，但必须设置 `AGENT_CLOUD_FALLBACK=true`，并显式提供 API Key 和模型名。云端只接收字段画像、质量摘要和业务问题，不接收原始 Excel/CSV 行。

模型名称不内置为“永远可用”的云端默认值，避免免费模型调整后静默漂移。

## 10. 当前真实边界

- 单文件页面已支持画像、质量、清洗、指标、分组、趋势、Top N、确定性计算、TaskRun 和证据导出；
- 交互式多文件上传、双表/三表受控关联和金额对账已经开放并通过核心与浏览器测试；
- 当前比例计算适合“符合条件的去重对象 / 全部去重对象”，尚未实现任意两个聚合量之比；
- 金额对账自动识别常见金额字段名，非常规字段名尚缺人工指定入口；
- 主计算引擎与 DuckDB-WASM 复核引擎都在浏览器本地运行，原始明细不上传；两者共享已确认口径和数据版本，因此独立性针对计算实现，不代表业务定义已被外部审计；
- TaskRun 持久化、基础限流、条件式所有者隔离、健康检查和单所有者线上主流程烟测已完成；外部数据库连接、角色权限、第二身份隔离实测和正式用户测试尚未完成。

面试中应按上述边界描述，不能把已测试的核心引擎说成已经上线的企业数据平台。
